# Execution artifacts

The Artifacts tool collects files shared across all chats on one execution, including archived chats. When the execution has more than one chat, a **This chat | All chats** switch narrows it to the chat on screen (the list then follows the tab), and **All chats** is where it starts. With one chat there is no switch, since both would show the same files, and rows leave out the chat's name. On desktop it opens in the tools panel. On a phone it opens from the tools sheet.

The source of truth is the saved conversation. Agent replies contribute local file links, images, inferred paths and visualize HTML markers using the same Markdown scanner as the transcript. Message attachments contribute their existing attachment metadata. Tool calls, thinking and user-written local paths do not create artifacts. No filesystem crawl, extra artifact record or agent registration step is needed.

Entries show their filename, original path and source chat. Repeated references to one file collapse to the newest reference. Relative and absolute paths inside the execution folder share an identity. Files retain their source chat when opened, so the existing preview routes apply their normal access checks. Missing files retain an entry and show the existing unavailable-file state.

Opening an entry uses the common artifact viewer and its copy, download, large view and beside placement controls. On desktop a file opens as its own panel tab, and closing it returns to Artifacts. Previous and Next stay within the artifact list rather than mixing it with transcript cards. Older entries load by themselves as the end of the list comes into view, and keep loading while it stays in view, so a filter that leaves the list short searches the whole history with no button to press.

`artifacts.list` is a typed tRPC query scoped by execution (every chat on it) or by one session (that chat alone, also the scope for chats without an execution). It authorizes the requested resource and filters sibling chats through the common catalog policy. The partial index `idx_chat_events_artifact_message` holds every agent reply and every message with attachments, and most replies share no file: in a real Home's longest chat, 6 of its newest 2,000 candidates carried one. So a page fills with files, not messages (`ARTIFACT_PAGE` in `execution-artifacts.ts`): it reads candidates in batches of 200 (201 per chat, merged in memory) until it holds 50 files or has read 2,000 candidates, then returns a cursor if more remain. 2,000 candidates is about 1 MB of text and a few milliseconds, so a page can come back short or empty with a cursor, and the client keeps going. The shared literal partial-index predicate excludes tool logs. A `(created_at, id)` cursor seeks into each chat independently, so paging does not sort a whole execution's events in SQLite or read provider raw payloads.

The client fetches only after the tool has been opened, refreshes every 15 seconds while it is visible and offers manual refresh. Search and loaded pages survive switches between chats on the same execution. The gallery's Execution artifacts example uses the same list and preview controls with fictional files.

Migration 0033 adds only the partial index. It applies when a Home's server next starts, through the normal migration runner.

## Files the agent read

A transcript's tool rows name files too (Read, Write, Edit). Those aren't artifacts, but their chips open the same way: a file the agent only read opens in the common artifact viewer, beside the chat or large with the switch between them, like a file in a message. Its chip is the trigger, not one of the chat's cards, so Previous and Next go from it through the chat's shared files without walking every file the agent read. A file the agent changed (a chip with a diff) opens in Files at its change, the view made for reviewing it. The viewer reaches a read file outside the chat's folder by the file viewer's rule (`named-files.ts`): a file tool call in this chat or its execution named that exact path. `/api/sessions/:id/reply-image` applies the same rule to images, outside a team Home.
