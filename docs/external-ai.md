# Ri in other agents

Settings → Ri in other agents adds Ri's MCP server to an outside agent, such as Claude Code, Codex, Cursor or ChatGPT. It can search, read and update tasks, notes, areas and the priority deck in your personal Ri. This includes private notes and private planning on tasks brought into My Ri from teams. Shared task edits still go through their team's normal command path. A team's own section, Team in other agents, gives an agent the team's shared work only.

**The name says the direction.** Ri's own agents are its workspaces, and Plugins bring things into Ri (Connectors, and MCP servers Ri's agents use). So this section is named for Ri going out into other agents, its header reads "Use Ri in other agents through MCP", and its description says Ri's MCP server is added to them, never an MCP server added to Ri. Its copy calls Claude Code, ChatGPT and the rest agents, not apps, since Apps in Ri are personal apps. It sits low in Settings, after Imports, because it's optional and mostly for people who already use a coding agent, and its first line says so: "You don't need this to use Ri." The engines Ri runs on (Claude Code, Codex, Cursor, OpenCode, Antigravity) are in the list too, in the opposite role, so the item for the one this Ri runs on (`defaultHarness`) says "Ri runs on this" and that setting it up is only for using that agent on its own. Once an agent has a key, its item gives one thing to ask it ("What's on my plate in Ri?"), which shows what the connection is for and, asked, is the agent's first request. Settings search reads descriptions, so searching "MCP" finds it beside Plugins. It was "Connect your agent" from 2026-10-27 until 2026-11-18, and MCP access before that. Its id, `external-ai`, stays, since links carry it.

To use a team from your personal Ri, follow [Testing a team through personal Ri](team-testing.md). It covers both MCP CRUD and running a shared task with your personal agent.

## The list

Every agent Ri knows is one accordion item, most popular first: Claude Code, Codex, Cursor, VS Code, then the Claude app, Gemini CLI, Windsurf, OpenCode, Antigravity, Goose, Kiro and LM Studio, then ChatGPT (which signs in instead of taking a key, [MCP sign-in](mcp-oauth.md)), another Ri and any MCP client. `AI_CLIENTS` in `src/lib/external-ai/client-config.ts` is the single source of each one's steps, install link, setup prompt, configuration file and skill folder. The personal settings page and a team's settings render the same list (`src/components/settings/connect-agents.tsx`), each with its own address and names.

Each item holds, in this order:

1. **Set up**, on a personal Ri, for an agent installed on the computer running Ri. In one action it makes the agent's key, writes Ri's server into the agent's user-level configuration the agent's own way, and installs Ri's skills for it. Until the agent's first request, the item says it's waiting for the agent to reach Ri, with the one thing to do there (usually start a new session). It says Connected only once the key has been used, since an agent that can't reach Ri never uses it. While an agent is waiting, Settings reads the key list every few seconds, so Connected appears while the person is still in the agent. Disconnect removes the entry Ri wrote and revokes the key.
2. **The agent's own install link** where it has one that opens the app directly: Cursor (`cursor://anysphere.cursor-deeplink/mcp/install`), VS Code (`vscode:mcp/install`), Goose (`goose://extension`) and LM Studio (`lmstudio://add_mcp`). The key is in the link, so Ri never uses an agent's web redirect (`cursor.com/en/install-mcp`, `kiro.dev/launch/...`), which would send the key to a web server. Kiro's only link is a web page, so Kiro gets Set up and its steps instead. The desktop app opens only these exact links from its main frame (`agentInstallUrl` in `desktop/trust.ts`).
3. **Copy setup prompt**: a prompt with a new key that an agent on another computer follows to set itself up.
4. **The steps by hand**, complete, with copy buttons. The step that holds the key shows a placeholder and Create key until the key exists. A key is shown only while Settings is open.
5. **The agent's keys**, each with when it was last used and Disconnect. Keys stay revocable per agent: `api_keys.client` records which agent a key was made for. Keys from before it was recorded are filed by their default name ("Claude Code", "Codex", "My Ri"), and any other under Any MCP client.

The agents Ri sets up on this computer, and how:

| Agent | Where Ri writes | How |
| --- | --- | --- |
| Claude Code | `~/.claude.json` (`$CLAUDE_CONFIG_DIR`) | `claude mcp add --transport http --scope user ri <url> --header "Authorization: Bearer <key>"` |
| Codex (CLI and the Codex app in ChatGPT.app) | `~/.codex/config.toml` (`$CODEX_HOME`) | `codex mcp add ri --url <url>`, then the key as `[mcp_servers.ri.http_headers]`, read back with `codex mcp get ri --json` |
| Cursor (editor and CLI) | `~/.cursor/mcp.json` | file, `mcpServers.ri = { url, headers }` |
| VS Code | the profile's `mcp.json` (`~/Library/Application Support/Code/User/mcp.json` on a Mac) | file, `servers.ri = { type: "http", url, headers }`, what `vscode:mcp/install` writes |
| Claude app | `claude_desktop_config.json` | file, through `npx mcp-remote <url> --header "Authorization:${RI_AUTH_HEADER}" --transport http-only` with the key in `env` |
| Gemini CLI | `~/.gemini/settings.json` | file, `type: "http"` with `url` (`httpUrl` is deprecated) |
| OpenCode | `~/.config/opencode/opencode.json` | file, `mcp.ri = { type: "remote", url, enabled, oauth: false, headers }` |
| Antigravity | `~/.gemini/config/mcp_config.json` | `agy mcp add --header ... ri <url>`, then the file narrowed to its owner |
| Kiro | `~/.kiro/settings/mcp.json` | file, `mcpServers.ri = { url, headers }` |

Files are edited in place with `jsonc-parser`: comments and everything else stay, a linked file (a dotfiles folder) is written where it really is, and the result is mode 600. A file that isn't valid JSON is left alone. An entry under Ri's name that isn't a Ri's is left alone too. Windsurf, Goose and LM Studio have steps but no Set up: Windsurf became Devin Desktop in June 2026 and which of its two files an install reads isn't documented, Goose keeps its extensions in YAML, and LM Studio's file has no documented place.

The key goes where the agent reads it: in its own user-level configuration, never in a project's files, and never through a shell, so it reaches no shell history. Steps a person follows keep it out of history too. Claude Code's put it in a shell-profile variable that its stored header names (`${RI_MCP_TOKEN}`), and the other steps are file edits. ChatGPT never takes a key: it reaches an MCP server only from OpenAI's cloud, with an OAuth sign-in or none, so it signs in to Ri ([MCP sign-in](mcp-oauth.md)). Its item gives Ri's address and the steps in ChatGPT, asks for a remote address first, and lists its connections with when each was last used and Disconnect. A connection is its own key, separate from your devices, so disconnecting it touches nothing else. The Claude app's own connectors work the same way from Anthropic's cloud, so its item offers them beside the local bridge, which still needs no remote address.

What's connected is read back from each agent's configuration, never stored on the side. Ri's entry is the one under its server name whose key is one of this Ri's working keys. A personal Ri is `ri` and a development one `ri-dev` (`personalMcpNames`), so trying a change never replaces the connection to the real one. A team is `ri-<team>`. If someone removes the entry by hand or revokes its key, the item shows that. An entry with one of this Ri's keys at another address on this computer is out of date (`stale: 'moved'`): the server moves it as it starts (below), and the item asks to set it up again only if that didn't happen. Setting an agent up again replaces Ri's earlier entry and revokes the earlier key.

Sources, checked 2026-10-27 against each agent's docs and, where installed here, its CLI: [Claude Code](https://code.claude.com/docs/en/mcp), [Codex](https://learn.chatgpt.com/docs/extend/mcp), [Cursor](https://cursor.com/docs/context/mcp) and [its install links](https://cursor.com/docs/context/mcp/install-links), [VS Code](https://code.visualstudio.com/docs/agents/reference/mcp-configuration), [mcp-remote](https://github.com/geelen/mcp-remote), [Gemini CLI](https://geminicli.com/docs/tools/mcp-server/), [Devin Desktop (Windsurf)](https://docs.devin.ai/desktop/cascade/mcp), [OpenCode](https://opencode.ai/docs/mcp-servers/), [Antigravity](https://antigravity.google/docs/mcp), [Goose](https://github.com/aaif-goose/goose/blob/main/documentation/docs/getting-started/using-extensions.md), [Kiro](https://kiro.dev/docs/mcp/configuration/), [LM Studio](https://lmstudio.ai/docs/app/mcp/deeplink), [ChatGPT](https://developers.openai.com/apps-sdk/build/auth).

## Agents and the CLI

Ri's main chat, or any agent on the computer running Ri, connects an agent when asked ("connect Codex to Ri") with the `connect_agent`, `disconnect_agent` and `list_agent_connections` actions (`src/lib/actions/agent-connection-actions.ts`). They're refused for a caller on another device, since they change files on the computer running Ri, and on a team. A person at a terminal uses the same actions as `ri mcp connect <agent>`, `ri mcp disconnect <agent>` and `ri mcp list`. Agents are named by their id, with or without dashes (`claude-code`, `gemini-cli`), or a short name (`claude`, `gemini`, `code`, `agy`).

## Skills

Connecting an agent on this computer puts Ri's skills (`agent-work-tasks-notes_ri` and `agent-browser_ri`) in that agent's own skill folder in the same action (`inspectSkillFolders` and `installGlobalSkills` in `src/lib/agent-skills/shipped.ts`). Another live Ri's copy of the same skills counts as installed, and someone's own skill under the name stays. First-run setup still installs them for every harness, so agents here can use the `ri` command even before they connect. The end of the section shows them with one-click install and uninstall. An agent on another computer gets the essentials over MCP itself: the content server's instructions carry the skill's writing conventions (`contentInstructions` in `src/app/api/home/[transport]/route.ts`).

## Address

For access from another computer, set an HTTPS remote address in Settings → Devices. Use any supported tunnel or your own HTTPS setup with a certificate everyone trusts (Beamd, Cloudflare Tunnel, Tailscale Serve and ngrok all have one). The computer running Ri must stay on and reachable. Ri does not configure a tunnel automatically here. With no remote address, the steps give the local address and say it works only on the computer running Ri. If you change the remote address later, update existing configurations by hand, or disconnect and connect again.

On the computer running Ri, an agent uses Ri's plain HTTP address on loopback (`getLoopbackBaseUrl` in `src/lib/auth/bootstrap.ts`), never the HTTPS address the desktop app opens. The always-on service and `ri start --http2` serve HTTPS with a certificate from Ri's own local authority, there for HTTP/2 in the app's window. Only the desktop app trusts it: it accepts that one certificate inside its own window and never adds it to the computer's trust store. Every other client, on every operating system, refuses the connection, often without saying why. So the HTTPS address stays between the desktop app and its service, and everything else on the computer goes to the server behind it, as Ri's own chats always have. Loopback never leaves the computer, so TLS there protects nothing. The service keeps that server's port in its settings across restarts, so it's a stable address to write into an agent. A Home served over plain HTTP (`ri start` from the command line, which records port 4224) uses its one address for both.

Set up writes that address, and so do the steps when there's no remote address. A team does the same on the computer hosting it: an agent there gets the team's loopback address, and members elsewhere get its remote one. The team's own AI chats reach its MCP and its `ri agent` commands there too (`configureTeamSession`), and so does a Buzz bridge when there's no remote address. MCP sign-in answers on that address as well ([MCP sign-in](mcp-oauth.md)).

When the address moves, agents follow it. As a personal Ri's server starts, `repairLocalAgents` points every entry with one of its working keys at another loopback address (such as the HTTPS one earlier versions of Set up wrote) to the current one, keeping the key. A remote address someone chose stays. It runs only in the server, where the address is certain: an `ri` command with the server stopped could only guess it.

A connection supplies tools to the agent you're already running. It does not create a chat inside Ri or require a new AI provider key. Search uses the existing semantic-search setup when available and falls back to keyword search. The key authenticates to Ri, not to Claude or OpenAI. A request to the MCP endpoint without a working key gets a 401 whose `WWW-Authenticate` points at Ri's sign-in (RFC 9728), so an agent that supports OAuth can sign in instead of holding a key. Other routes refuse plainly.

For a team, join as a member first. Each key belongs to the signed-in member, and its writes are attributed to that member as AI actions. Making another key does not create another person. Set up belongs to a personal Ri, which runs on the member's own computer, so a team's list has the steps, links and setup prompt. A personal Ri's key acts as its owner and is not a multi-user signup mechanism.

Agents can also sign in to Ri's MCP with OAuth instead of holding a key: ChatGPT and Claude's connectors from the cloud, and Claude Code, VS Code or any client that supports MCP authorization on this or another computer. See [MCP sign-in](mcp-oauth.md). A sign-in makes the same kind of key, filed under the agent it proved it is.

## Implementation and boundary

The endpoint is `/api/home/mcp`. Tools reuse the action registry and domain queries, including mirrors, embeddings and shared-task forwarding. `HOME_CONTENT_ACTIONS` in `src/lib/external-ai/policy.ts` is the explicit tool allowlist. New registry tools do not automatically become external tools, and the agent connection actions are not among them. The proxy permits only this endpoint for a personal external key, strips caller-supplied authority headers and marks its scope. MCP discovery and dispatch enforce the scope. Dispatch checks the live key again before each tool, including revocation and expiry. A supplied Ri session credential never makes an external assistant a Ri chat.

Personal external credentials use the existing `api_keys.role = ai_client`, with both `device_id` and `member_id` null, and `client` naming the agent (migration `0026_ai_client_kind`). Only a personal viewer can manage them, through `externalAi` tRPC: `create` (a key for one agent, returned once), `list`, `revoke`, `address`, and for this computer `local`, `setUp` and `disconnectLocal`. A team AI client still requires an active member (`team.aiClients`, with `address` for its steps). Device-bound AI keys remain invalid in a personal Ri. Host-key backfill assigns only sign-in keys, so startup cannot attach external clients to the host.

These keys cannot sign into a browser, open a WebSocket, use the natural-language `/api/mcp`, start agents or chats, use terminals, change settings or read attachment files. They can add to the capture stream (`create_stream_item`) but never read it, and search excludes it. They can read Ri's user guide (`read_docs`), the same public pages as https://ri.app/docs. Apps that draw Ri's view show the person their Stream, scratchpad and calendar through view-only tools the model doesn't see ([MCP sign-in](mcp-oauth.md), "The app"). Body updates support `expected_body_revision` so clients can avoid replacing newer text. Existing viewer and signed-session MCP behavior is unchanged.
